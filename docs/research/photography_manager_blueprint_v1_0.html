1. 产品定义与价值边界

1.1 一句话定义

照片仍在自己的硬盘上；软件负责让它们容易找、容易选、容易调整，并让原片、编辑版本和成片始终对应得上。

“轻量”主要指安装和使用负担、资源占用、信息结构和不必要功能，而不是删除可靠的管理能力。不能做成只能打开文件夹的看图器，然后称为 LRC 替代品。

1.2 核心工作流

已有照片目录 / 存储卡
       ↓
引用已有文件 / 安全复制到指定目录
       ↓
浏览 → 比较 → 评级 → 关键词与集合
       ↓
基础显影与裁剪
       ↓
少量照片进入外部精修
       ↓
成片回收与版本关联
       ↓
批量输出 / 历史归档 / 离线查找 / 以后再编辑

正式版必须把这条链条跑通。不能用“外部工具能处理”掩盖缺失的任务交接，也不能用“先备份”代替产品自身的文件安全设计。

1.3 第一批服务的用户

第一批用户是有相机 RAW、有自己文件夹习惯、主要独自管理照片的 Mac 摄影者。数量可以从几千张逐渐增长，照片可能位于本机或外置硬盘，精修频率低于浏览、选择和整理频率。

暂不以商业摄影团队、多机并发协作、新闻机构资产管理、视频后期、专业印前和云端交付为目标。不是这些需求没有价值，而是它们会改变数据模型、权限和维护范围。

1.4 产品成立的验证方式

使用同一组真实拍摄资料，对比现有工作方式和本 App 的完整流程，记录操作次数、错误、等待、遗漏及主观满意度。重点判断：是否更容易找回照片，是否愿意每天用它选片，基础输出是否可接受，外部精修是否顺畅，是否信任其文件操作。

不能只凭“界面更好看”“没有订阅”“支持 RAW”宣布竞争力。Nitro 已提供 Apple RAW、文件系统工作流、XMP 和非破坏性编辑等能力，是必须实际试用的直接参照。S16

2. 第一正式版范围

本节定义的是 V1 正式版，不是第一周原型。开发可以分阶段，但发布时不得把关键流程长期留在占位状态。

2.2 V1 不做的内容

不做自研 RAW 解码器、专业蒙版和局部修复、AI 降噪模型、联机拍摄、全景/HDR 合成、视频管理与转码、云端图库、团队协作、地图和印刷排版。暂不接入 Apple Photos 库；不直接读写 .lrcat；不保证 Adobe 预设或调色一比一还原。

高级曲线、复杂 HSL、镜头配置数据库、相机胶片模拟、面部识别、语义搜索和插件市场均后置。界面不放未实现的灰色占位模块制造“功能很多”的错觉。

2.3 允许的能力降级

降级必须清楚显示且不伤数据。例如某 RAW 只能管理和查看内嵌预览，就标记“当前系统不支持显影”，仍允许评级和外部处理。缺少完整原片时，禁止假装正常导出全分辨率成片。

不能把正式版必需功能不成熟解释为“轻量化”。如果 G1 证明 Apple 显影不满足目标样本，应评审产品范围或外部处理比重，不自动转向自研专业引擎。

3. 核心概念与操作语义

3.1 必须区分的六个概念

概念 含义 不能混淆的地方
目录 Catalog 管理记录、关系、编辑参数和任务的数据库 不是原片备份，也不等于 Finder 文件夹
照片资产 Asset 用户理解的一次拍摄或一张照片 可以对应多个文件，不按扩展名重复算多张作品
文件 File 磁盘上实际存在或曾经存在的文件 文件路径可变，不能作为唯一身份
版本 Version 基于某个源文件的一组处理定义或已生成成片 最新版本不一定是用户采用的版本
集合 Collection 逻辑组织方式 加入集合不复制文件，从集合移除不删除文件
预览 Preview 某版本、尺寸、引擎及处理状态下的显示材料 可重建缓存不等于用户作品，离线预览不等于可编辑 RAW 代理

LRC 采用目录记录文件位置及相关信息的模式；本项目借鉴这种组织思想，不借用其私有数据库作为自身存储。S12

3.2 元数据与调整的作用范围

默认评级、标记、关键词和标题属于照片资产；某个文件特有的 EXIF 属于文件；曝光、白平衡和裁剪属于版本。RAW 与 JPEG 成对时，资产评级同步显示，但二者的显影配方不能混用。

多个文件初始元数据不一致时先记录来源并提示，不能因为建立了配对就覆写其中一方。用户可以拆分错误关联，再独立管理。

3.3 三种不同的删除

“从集合移除”只改集合关系；“从目录移除”只删除管理记录并保留文件；“移入废纸篓”才处理磁盘文件。默认 Delete 键不直接永久删除原片。

移入废纸篓前必须展示物理文件清单、关联文件数量和影响范围。拒绝标记不是删除。不得定时自动清除拒绝照片，不得在不支持废纸篓的目标上静默降级为永久删除。

3.4 同名与重复不是同一个问题

不同文件夹里的 DSC0001 可能来自不同拍摄；相同内容在不同位置可能是有意保留的副本。默认不自动去重删除，不用“文件名＋日期”强行合并资产。指纹只辅助识别和复位关联，涉及合并必须可预览与撤销。

4. 信息架构与界面行为

4.1 主窗口

建议使用原生 Mac 三栏结构：左侧来源与集合，中间网格/查看器，右侧元数据/编辑检查器。底部胶片带按需出现，长任务放在统一任务中心，而不是每个动作弹一个阻塞对话框。

顶部：返回 / 当前范围 / 搜索与筛选 / 视图切换 / 任务 / 输出

│ 目录与来源 │                        │ 信息 / 编辑 │
│ 文件夹     │ 网格 / 单图 / 双图比较  │ 版本 / 文件 │
│ 集合       │                        │             │
│ 快速筛选   │                        │             │
├───────────┴────────────────────────┴─────────────┤
│ 可选胶片带 · 选择计数 · 原片/预览状态 · 后台任务摘要 │
└─────────────────────────────────────────────────┘

这是布局说明，不是最终视觉稿。调色时使用低干扰、中性的照片背景，避免把现有装饰 App 的强视觉模板语言带入画质评估界面。

4.2 视图与选择规则

网格到单图再返回，保留滚动位置、筛选和焦点。界面必须区分“活动照片”和“选中的多张照片”。批量评级、批量导出明确作用于选择集；编辑面板默认只修改活动版本，批量同步需要明确动作。

筛选后照片被改成不满足条件时，不要立即让键盘焦点随机跳动。定义稳定的下一张规则，并允许用户撤销后找回刚操作的资产。

双图比较提供固定参考图、切换候选图、同步/独立缩放。同步缩放以规范化画面位置为基准；不同尺寸或裁剪状态下显示不可完全对齐的说明，而不扭曲图片。

4.4 必须有的状态设计

空目录、扫描中、部分失败、权限失效、根目录离线、文件缺失、仅预览、不支持显影、渲染中、配方保存失败和磁盘不足，各自有明确状态及恢复入口。不能用一个红色感叹号表示全部问题。

VoiceOver 标签、键盘焦点、对比度、减弱动态效果和窗口缩放必须纳入实现，不留到发布最后补。关键保存失败不能只用一闪而过的 Toast。

5. 导入、扫描与存储介质

5.1 两种明确入口

添加已有照片只建立索引；必须明确“不会移动或复制原片”。用户选择文件夹后，显示发现文件数、可管理类型和异常摘要，可边扫描边浏览已发现内容。

从存储卡/文件夹复制要求用户选目标目录、命名模板和冲突策略。V1 支持以文件系统可访问的存储卡/目录为源，不把 USB/PTP 相机直连当作已经支持。

复制导入绝不自动清空存储卡。没有验证成功、没有明确错误清单，就不能显示“全部导入完成”。

5.2 复制导入流程

建立任务清单
→ 检查读取授权、目标写入权限、估计空间与文件名冲突
→ 对每个文件复制到目标卷的临时名称
→ 完成写入并回读校验；原文件复制前后若变化则暂停该项
→ 同卷发布到最终名称，默认不覆盖
→ 写入目录记录与资产关系
→ 汇总成功 / 已存在 / 冲突 / 失败 / 取消

完整性验证使用内容摘要等可靠方式；仅比较文件大小不能作为“内容一致”的证明。必须处理只读存储卡、复制中断、源卷断开和目标磁盘已满。

同一组 RAW/JPEG/附属文件的复制不是天然原子事务。任务清单逐项记录状态，全部需要的项完成后再标记整组完成；失败时保留可解释的部分结果，不盲目删除用户文件。

5.3 扫描分层

第一遍只收集路径、类型、体积、基本身份和轻量元数据；随后按可见性提取缩略图、完整元数据及关联建议。完整 RAW 渲染不得阻塞首次目录出现。

支持暂停、取消、继续与增量重扫。取消停止新任务并清理本任务临时资源，已完成记录保留。中断重启不重新产生一套重复资产。

5.4 监视与重新校验

FSEvents 用作“需要复查哪里”的提示，不作为完整文件真相。官方文档说明丢失/合并事件等情况需要重扫相关目录；监听必须配合重新校验、根目录身份检查及定期/用户触发的扫描。S08

扫描未完成、权限失效或磁盘离线期间，不得把未见到的文件标记为已删除。只有对应范围已成功扫描且确认可访问，才能将未发现文件标记为“疑似缺失”，保留管理记录供重新定位。

不跟随未知符号链接无限递归；识别已扫描根目录重叠，避免重复统计。导出目录、任务目录和缓存目录必须有排除/来源规则，避免输出又触发导入的循环。

6. 组织、检索与资产关联

6.1 文件夹和集合

文件夹反映真实目录；普通集合保存资产引用和用户排序；集合分组只组织集合。智能集合采用受限规则模型，首版支持评级、标记、关键词、日期、文件类型、相机/镜头、离线状态和编辑状态的 AND/OR 组合，不执行任意脚本或 SQL。

集合内手动顺序与全库按拍摄时间排序分别保存。移动到集合不是移动文件；把文件拖进真实文件夹时必须有不同的操作反馈。

6.2 关键词与搜索

支持关键词增删、批量赋值、常用关键词建议及简单层级。对中文关键词先确保准确的包含/前缀搜索和规范化，不默认声称通用全文分词已经支持中文。数据库索引和查询语义应有真实中英文样本测试。

日期保存原始拍摄时间文本、可解析值和可用时区信息。没有时区的 EXIF 不得被无提示转换成用户当前时区；不要因跨时区旅行而把照片错误归到另一日。

多条件筛选显示可清除的条件标签；筛选结果计数与选中计数分开。大型查询分页返回，不能全表读取后在主线程过滤。

6.3 RAW＋JPEG 配对

依据同目录、文件名模式、拍摄时间、图像标识和相机信息提出关联建议。只在匹配唯一且满足规则时自动组合；存在冲突时交给用户确认。改名或跨文件夹时保留关联，不重建为两张无关照片。

配对后默认网格显示一个资产和格式徽标，可展开查看。删除其中某个文件必须明确该文件，而不是把整个资产当一个可直接删除的路径。

6.4 原片、版本与外部成片

资产可以有多个可选择源文件和多个编辑版本。默认展示版本由用户选择；最近修改不会自动替换“已采用”版本。外部 TIFF/JPEG 保存自己的来源版本、创建任务、色彩配置和路径。

对历史成片，自动匹配只给候选；不以图像相似或名称相近就直接合并。V1 必须有手动“关联到原片”“解除关联”和“设为采用版本”。

6.5 离线行为

原片离线时允许浏览已有预览、评级、关键词和集合整理。V1 不提供依靠小 JPEG 代理继续 RAW 显影的假能力；编辑、1:1 检查和全分辨率导出在原片不可用时明确禁用。

用户可以显式“保留离线预览”，该内容不随普通缓存自动清理；它仍不等于原片备份。重新连接硬盘后先校验文件身份，再恢复操作。

7.2 为什么不从 LibRaw 搭专业处理链

LibRaw 提供 RAW 数据、必要元数据和内嵌预览提取，也有基础转换；官方明确将生产级完整渲染排除在其主要范围之外。因此它不是接入即可得到 LRC 显影质量的完整编辑 SDK。S18

LibRaw 只作为具体兼容缺口的候选，不作为 V1 默认兜底。即使未来用于提取预览，也需要额外测试和许可证审查。不能为支持一个特殊文件，就未经评审扩大到自建相机色彩与降噪管线。

7.3 外部开源工具的正确位置

darktable CLI 可以按输入、处理历史/附属文件和输出配置导出；RawTherapee 也有命令行处理入口。这些是批处理接口，不是已经可以嵌入 SwiftUI 的稳定实时编辑 SDK。S19

V1 不内置它们的专业处理代码。用户自行安装工具，App 先管理文件交接和成片回收。深度嵌入、捆绑二进制或紧耦合通信，必须先形成独立的技术与许可证 ADR。

7.4 与现有图片 App 的复用

可以评估复用：通用裁剪几何、导出任务 UI、文件选择、基础图像显示、国际化和部分参数控件。

不能未经检查复用：以 8-bit JPEG 为中心的流水线、假设 sRGB 的颜色处理、iOS 专用底部托盘布局、把临时文件视为可删缓存的策略、把所有效果压平的历史管理。

复用审查产物应列出“直接复用、需要适配、不复用”及原因。不要为了共享代码把两个产品强行绑成一个大型工程。

8. RAW 支持策略

8.1 支持等级按文件判断

等级 能力 对用户的展示
管理可用 可读取文件信息和建立资产 可整理；可能没有可视预览
预览可用 可读取内嵌/系统预览 标明预览来源，不宣称可显影
显影可用 当前系统可创建并渲染 RAW 处理管线 显示经探测可用的控件
输出已验证 全尺寸输出与目标格式、颜色一致性通过测试 才进入正式支持清单

“系统支持这个机型”不是对所有压缩模式、像素合成模式和文件变体的保证。Nitro 有自己的扩展 RAW 路径，不能把其相机清单直接当作纯 Apple API 的清单。S17

8.2 运行时能力探测

新文件建立 ImageCapabilities，记录能否解码、支持的解码器、可用调整、原始尺寸、预览来源、最大已验证输出和错误原因。界面依赖能力对象，不依赖文件扩展名的硬编码判断。

曝光、白平衡等核心调整也要检查输出和参数范围。对不支持的操作隐藏或明确说明原因；不创建能拖动却不改变画面的控件。

8.3 解码器版本不静默升级

创建编辑版本时记录实际采用的解码器及系统环境。已有版本优先使用原解码器；不可用时显示“原处理引擎不可用”，允许查看保留的预览、生成明确标记的新版本或交给外部工具。

不得静默换引擎后覆写旧配方与预览。保存了版本号也不代表未来系统一定保留该引擎，更不构成跨系统像素完全复现的保证。S02

Apple 的 WWDC26 资料介绍 RAW 9 与 macOS 27 等平台，并要求检查支持后显式启用；部分调整在新引擎中不再适用。本项目不把该新能力当作 macOS 14 的通用基础，也不按引擎编号猜测全部参数支持。S03

8.4 兼容验证清单

测试记录必须包含相机型号、固件信息（可获得时）、RAW 格式/压缩模式、位深/拍摄模式、系统构建号、解码器、样本摘要、打开结果、显影结果、输出结果和已知限制。

对缺少样本的机型标记“未实测”，不能写“已支持”。对损坏文件和极端尺寸限制也要给清楚错误，不能让一个坏文件阻塞整库。

9. 基础编辑与非破坏性版本

9.1 V1 调整能力

调整组 首版要求 实现边界
白平衡 原拍摄白平衡、温度/色调、复位；吸管可在验证后加入 RAW 与 JPEG 的白平衡语义分开，不伪造相机温度
曝光 明确的 EV 调整与数值输入 RAW 在 RAW 阶段执行；普通图像走相应滤镜，避免重复曝光
明暗 基础对比度；经样张验证的高光/阴影控制 有稳定映射才开放，不用同名滑杆冒充 Adobe 算法
色彩 饱和度与黑白基础控制 不承诺胶片模拟或相机原生 Picture Style 一致

高光/阴影等控制应在 G1/G3 建立具体滤镜和参数映射；没有通过样张测试不能用随意的亮度公式补位。基础调整不足时，应明确修订范围，不能称“专业调色已实现”。

9.2 配方与提交规则

调整只改变配方，不改原始像素。拖动中的参数属于编辑草稿；一次完成的手势合并为一个可撤销动作，配方持久化失败必须显式告知。失去焦点、切图或退出前需要提交，失败则保留草稿并允许恢复。

界面即时反馈与“已经可靠保存”分开。不能在异步保存尚未完成时误示保存成功。批量调整创建操作记录，每张照片独立记录成功/失败，不因其中一张不兼容而回滚已确认的其他资产。

9.3 版本分层

用户可见的“版本”是命名的处理方案或外部成片；内部“修订”是该版本的参数变更。每次输出都固定对应某个修订，后续滑动参数不会改变已排队输出的内容。

基线版本使用当前选定引擎的原拍摄白平衡与默认处理。所谓“调整前”不是完全未经处理的传感器数据，也不是相机内嵌 JPEG。界面可以额外提供“查看相机预览”，但必须单独命名。

9.4 几何处理契约

先建立经 EXIF 方向校正的规范源坐标，再应用用户旋转/镜像/拉直，最后在该变换后的画布内裁剪。配方明确记录坐标原点、归一化范围、变换顺序、源尺寸和画布规则；不得用当前屏幕坐标直接保存裁剪框。

所有 EXIF 方向、横竖图、镜像、旋转与拉直组合都进入几何回归测试。预览和全尺寸导出的裁剪区域必须一致。滤镜产生无限 extent 或变换后非零原点时，需要按同一契约处理。

10. 图像渲染、色彩与编解码

10.1 处理链

源文件与实际读取权限
  → 格式/方向/ICC/RAW 能力解析
  → RAW 解码与基础处理，或普通图像解码
  → 版本化的色调与色彩处理阶段
  → 统一几何变换与裁剪
  → 按用途缩放与输出处理
  → 显示目标或文件编码目标的颜色转换
  → 屏幕 / JPEG / TIFF

预览和输出共享同一处理定义、引擎及配方。显示分辨率与交互质量可以不同，但要标记粗预览状态，不能偷偷更换渲染引擎。

10.2 预览分层

层 来源与用途 生命周期
L0 轻量占位与文件信息 可重建
L1 内嵌/系统缩略图，快速进入图库 可重建；记录来源
L2 当前配方的屏幕尺寸显影预览 可重建；配方变化后失效
L3 按需高分辨率/局部细节预览 高优先级临时缓存；不承诺 RAW 局部解码一定省掉全图成本
Pinned 用户明确保留的离线预览 持久内容，普通缓存淘汰不得移除

内嵌缩略图不一定存在，也可能很小。Image I/O 的缩略图生成接口可作为系统路径，但不能保证每种 RAW 都能无完整解码地得到大图。S04

禁止首次扫描就为全库渲染 1:1。屏幕仅显示一小张图片时优先请求合适的缩放处理。细节评估时，1:1 必须确认真实像素来源，而不是把低分辨率预览放大冒充细节。

10.3 色彩契约

默认工作管线采用明确、可测试的宽容度浮点处理，候选为扩展线性 sRGB 与半浮点中间格式；最终选择由 G1 样张和滤镜语义验证冻结。Core Image 提供工作色彩空间与工作像素格式的配置能力，不应通过关闭颜色管理“解决色差”。S06

输入 ICC 必须识别并用于像素转换。缺失或损坏 ICC 时采用文档化的回退规则并标记，不把 RAW 的相机空间误当 sRGB。黑白、透明图像和特殊色彩模型也要测试，不能只测一张标准彩色 JPEG。

不同滤镜需要的处理语义在 ToneColorStage 中明确；不要假设所有滤镜都适合在任意空间和任意阶段调用。不能从设置面板的排列顺序直接推导真实渲染顺序。

10.4 SDR 优先与直方图

V1 面向稳定 SDR 编辑和输出，HDR/EDR 单独作为后续项目，不默认开启高亮显示然后导出不同观感的 SDR JPEG。具体 RAW 输出到 SDR 的设置和色调行为要成为测试基线。

直方图和高光警告默认基于当前显示/输出渲染，标注“渲染结果”。不把 RGB 输出通道裁切等同于传感器 RAW 通道已经过曝；V1 不承诺 RAW 传感器级曝光分析。

用途 V1 默认 必须说明
日常分享 JPEG，8-bit，sRGB，嵌入正确配置 可设置质量与尺寸；GPS 默认按隐私预设移除
外部继续编辑 TIFF，16-bit，sRGB 或经验证的 Display P3，嵌入配置 保留当前外观，不等于保留完整 RAW 调整余量
原片移交 字节不改的原文件副本＋选定附属文件＋清单 不烘焙本 App 调整，不声称对方可识别自有配方
管理信息迁出 JSON/CSV 清单，标准元数据子集与自有配方 清楚注明哪些信息目标软件可能无法识别

TIFF 位深、通道、实际 ICC 和尺寸应由输出文件回读验证，不以编码参数传入成功作为最终证据。V1 不默认输出无配置 TIFF，不使用低质量 JPEG 作为 RAW 调整链的中间格式。

PNG/HEIF 等可在通过验证后加入，但不影响第一条 JPEG/TIFF 主流程的发布验收。PSD/PSB 仅考虑作为外部工程附件保存，不承诺自己解析图层或显示所有格式。

10.6 渲染调度与内存

交互渲染和批量输出使用分别配置的处理上下文，不对每次滑杆变更创建新的重型上下文。可变滤镜实例不得跨并发任务无保护地共享。新请求优先于已经失去意义的旧请求，旧结果不得覆盖新状态。

RAW 9 的官方建议区分交互场景与批量导出场景的中间结果缓存策略；不能机械地全局关闭缓存或全局无限开启缓存。实现按目标引擎与内存测试决定，并限制同时活跃的大图数量。S03

初始调度建议：一个活动编辑会话优先，一条全尺寸输出任务，低并发后台预览。并发数由内存压力、磁盘速度和实际测量动态调整，不简单设置成 CPU 核心数。

例如 6000×4000 的 RGBA 半浮点单缓冲约需 192,000,000 字节（约 183 MiB），尚未包含其他中间图。此处只是 宽×高×4通道×2字节 的内存估算，不是实际任务占用测量。因此不能因为压缩 RAW 文件只有几十 MB，就假设十张并行解码仍然很省内存。

11. 外部编辑往返

11.1 两种交接模式

**模式 A：交给外部软件从 RAW 开始处理。**默认创建原始 RAW 的工作副本，并按明确关系复制需要保留的附属文件。外部工具操作工作副本，而不是用户唯一原片。它可以按自己的引擎重新显影，不承诺沿用本 App 或 LRC 的视觉效果。

**模式 B：交给外部软件继续处理当前效果。**冻结当前版本修订，输出经验证的 16-bit TIFF，嵌入选择的色彩配置。外部工具在此基础上精修，结果回收为该修订的派生成片。

RAW 工作副本和 TIFF 都可能较大。创建前预估空间，工作目录可配置到外置盘；只复制当前任务需要的文件，不复制整库。

11.2 为什么默认使用副本

本 App 可以保证自身不改原始像素，但不能保证外部编辑器绝不改原文件或附属文件。因此不能一边直接交出唯一原片，一边声称绝对非破坏性。

V1 默认不提供“直接编辑唯一原片”的捷径。未来增加高级模式时必须明确风险和备份责任，并与安全默认路径分开。

11.3 每次交接都是持久化任务

任务至少保存：任务 ID、资产 ID、源文件修订、输入版本修订、模式、目标 App 标识、输入副本、预期输出目录、已发现文件、确认的输出、开始/结束时间、错误和清理状态。

prepared → staging → readyToOpen → opened
        → waitingForResult → resultDetected → awaitingConfirmation
        → imported → completed

分支：cancelled / failed / interrupted / needsUserAction

打开应用成功不代表编辑完成；外部应用退出也不代表结果已保存。文件变化通知只能提出结果候选。候选需确认稳定、可解码并获得用户确认，或通过经过验证的特定工具协议确认。

11.4 可靠回收是基线，自动回收是增强

V1 必须有“选择编辑结果”操作，允许明确挑选一个或多个结果并预览来源关系。对受支持编辑器可以自动发现并建议，但没有可靠返回接口时不得伪造全自动能力。

不按“文件夹里最新出现的文件”猜来源。一个输入输出多张文件、另存为不同名称、编辑过程中产生临时文件，均不得关联错照片。

用户在外部编辑期间继续修改本 App 的版本时，返回结果仍关联到启动时冻结的修订，而不是悄悄挂到最新参数上。

11.5 成片与临时文件

确认回收后，成片进入用户选择的持久输出目录或明确管理的作品目录，并成为正常资产文件。不能把它一直放在系统临时目录，也不能让缓存清理器删掉它。

未完成的外部工作目录具有保护状态；自动清理不得删除外部工程、未识别附属文件或唯一结果。清理前展示输入副本、可删除中间件和需保留内容，并确认没有仍在进行的任务。

12. 元数据、XMP 与 LRC 迁移

12.1 四类信息分别处理

信息 本 App 的政策
拍摄信息 EXIF 读取和展示，保留原始值及来源，V1 不回写原片
评级、标签、关键词等管理信息 读取明确子集；本 App 修改先写目录；支持显式标准导出
本 App 的调整配方 自有版本化 JSON，目录保存并可迁出，不伪装成 Adobe 参数
Adobe/其他软件专有调整 不解释的内容原样保留，不宣称可以复现，不随意改写

Adobe 官方说明专有 RAW 的 XMP 通常在附属文件，JPEG/TIFF/PSD/DNG 等可能将 XMP 嵌在文件内。因此迁移不能只扫描旁边有没有 .xmp。S13

12.2 V1 元数据读取子集

优先验证 xmp:Rating、xmp:Label、dc:subject、常见标题/说明/版权字段及可用层级关键词。xmp:Rating 的拒绝值与普通 0—5 星分开映射，不能把拒绝自动变成普通未评级。颜色标签是文本，需显示映射并保留原字符串，不假定各软件颜色名称相同。

层级关键词保留原始字段及规范化结构，测试中文、转义、重名和多个父节点。作者、版权和拍摄时间不能因为导出清理隐私而一概丢掉。

同名 RAW＋JPEG 可能共享或分别拥有不同命名的附属文件。附属文件与源文件的绑定单独建模，遇到一对多或未知命名时不自动重命名，也不强行视为一对一。

12.3 默认不覆盖既有 XMP

本 App 的工作变更写入目录；显式导出到用户选择的目录，提供标准元数据文件和可读清单。源目录既有 XMP、ACR 等默认只读，原片内嵌元数据也不重写。

这是一项明确的兼容边界：**V1 支持标准元数据读取和导出，不宣称已经具备全面双向原位同步。**用户的整理结果必须可导出，不能只困在数据库。

后续若增加原位更新，必须实现命名空间级合并、未知字段保留、读前/写前摘要检查、备份、原子替换和外部改动冲突解决。不能用只包含本 App 理解字段的新 XML 整体覆盖旧 XMP。

12.4 冲突模型

每个导入字段保存来源、导入值/版本以及本地修改状态。外部文件后来变化时：本地未修改的字段可以在确认策略下刷新；双方都修改则生成冲突；删除字段也属于变化。

更新以字段为单位，不简单用“最新文件时间”覆盖全部记录。重新扫描不得抹掉用户离线时做的评级、关键词或集合修改。

12.5 ACR 与未知附属文件保护

Adobe 的官方文档确认较重编辑可能同时使用 XMP 和 ACR 附属文件。V1 不解读 ACR，但必须把已识别的关联文件纳入保留、复制和移动预览。S14

对未知扩展名，只能提出关联候选，不能猜测其内部路径或重写内容。对涉及共享附属文件或疑似专有路径依赖的重命名/移动，默认阻止危险自动操作，允许先导出副本与清单。

“原样保留附属文件”也不等于保证第三方工具在重命名后仍能识别它。因此 V1 对这类组合的最安全策略是保持名称，必要时移动整个拍摄目录而不是擅自重命名单文件；仍须经过确认和验证。

12.6 LRC 迁移方案

迁移前：备份 LRC 目录与原片；由用户在 LRC 中保存可导出的元数据。重要的既有调色成果另行导出成片。此操作由用户在 LRC 中执行，本 App 不改其目录。

迁移中：引用原片目录，读取嵌入及附属元数据；导入已修成片，提出关联候选；生成“成功、缺失、冲突、不支持、未迁移”的报告。

迁移后：抽查评级、关键词、日期、文件数量及成片关联；保留旧 LRC 目录，不在迁移成功后删除旧资料。没有导出的虚拟副本和只在旧目录中的关系不能凭空恢复。

12.7 可以迁什么，不能承诺什么

14.2 数据库不变量

每个版本必须有有效的来源关系；采用版本必须属于同一资产；一个位置不能被重复索引成多条活动文件记录；外部任务返回结果必须关联其冻结输入修订；集合删除不能级联删除磁盘文件。

启用外键与必要的唯一约束。涉及资产合并/拆分、版本切换和批量元数据时使用事务。索引覆盖常用排序、根目录相对路径、评级、日期、相机、集合成员及任务状态。

查询规则 JSON 与编辑配方 JSON 是版本化的结构化数据，不保存任意 SQL。绝不把整个图库序列化成一个巨大的 JSON 文件作为主存储。

14.4 数据库版本与 SQLite 选择

优先选择 SQLite＋清晰的 Swift 封装；GRDB 是候选工具，而不是回避 SQL/事务设计的理由。S11

数据库默认本地、单 App 实例写入。WAL 不能放在跨主机网络文件系统上；WAL 文件属于运行中持久状态的一部分，不能只复制主数据库文件就声称做了完整备份。S09

**实施新增检查：SQLite 官方在 2026-03-13 的 3.51.3 发布中修复了 WAL-reset 数据库损坏问题。**发布构建必须记录真实链接的 SQLite 版本与补丁来源，不能仅因 GRDB 是新版本就推断底层 SQLite 已包含修复。S10

T02 要决定使用明确包含修复的 SQLite 构建，或采用经过验证的保守日志/连接策略。未确认补丁状态时不默认启用复杂的多连接 WAL/检查点并发。写入、检查点、备份和恢复由统一存储服务协调。

14.5 迁移与恢复

每次 schema 升级前先创建可恢复快照，再执行有事务边界的迁移；迁移失败保持旧目录可恢复，不能进入半升级界面。新 App 能读取受支持旧目录，旧 App 遇到较新格式必须只读拒绝或明确停止，不尝试降级写入。

目录恢复后先检查关系完整性与操作日志，再对外部文件做状态核实。目录备份只恢复管理状态，不会把被其他软件永久删除的原片变回来。

15. 文件安全、事务与恢复

15.1 安全等级

复制导入 保留源、回读校验、失败可继续

15.2 数据库事务不能覆盖文件系统

SQLite 提交和磁盘移动不是一个共同的原子事务。实现采用持久化操作日志：先落地意图，再执行可验证步骤，随后更新目录，最后标记完成。崩溃后根据源与目标身份恢复，而不是无条件重跑。

异常：blocked / partialFailure / interrupted / recoveryRequired

每一步记录预期文件身份、目标和结果；恢复只能在确认对象仍然是本次任务操作的文件时执行。其他软件后来改写的文件不能被补偿逻辑覆盖。

15.3 同卷与跨卷

同卷单文件重命名可以利用文件系统提供的原子能力，但一组原片、JPEG、多个附属文件不是天然原子的。必须按组计划、逐文件记账，并在结束后校验关系。

跨卷移动通过复制、校验和发布目标完成，再按明确策略处理源。中断时宁可留下经说明的两份文件，也不要为了“看起来完成”删掉唯一完整副本。对源被外部修改的情况停止，要求重新评估。

15.4 磁盘不足

写入大文件前预估输出、临时文件和管理数据所需空间，并保留管理日志的安全余量。估算不可靠时以保守策略处理。磁盘不足首先暂停可重建预览和新输出，不去删除用户作品“腾空间”。

所有写入步骤处理实际的空间错误，不能只做一次开始前检查。数据库提交失败、临时文件未完成和复制源仍在时，给出一致恢复说明。

15.5 撤销与恢复承诺

评级、集合和编辑配方支持正常撤销。文件操作只在具备可验证的逆操作条件时提供撤销；废纸篓被清空、目标被覆盖或原卷丢失时不能保证恢复。

不要在界面写“所有操作都可撤销”。明确说明“从目录移除”如何重新导入，“移入废纸篓”如何尝试恢复，以及何时只能使用用户自己的原片备份。

16. 缓存、任务调度与空间预算

16.1 四类数据不能共用清理策略

可重建缩略图/预览是缓存；用户固定的离线预览是持久选择；编辑配方和目录是用户数据；外部工程和导出成片是作品。后面三类不进入自动缓存回收。

初始建议：可重建磁盘缓存上限 5GiB，提供 1/5/10GiB 与自定义选项；这只是初始产品配置，G2/G4 根据预览成本实测修订。固定离线预览另计并显示容量，不能悄悄突破用户以为的“总占用”。

设置页显示数据库、普通缓存、固定预览、外部任务及成片目录的占用和位置。区分逻辑文件大小与实际可回收空间，涉及文件系统共享块时不声称两者必然相同。

16.2 缓存键

缓存键至少包含：源文件身份与内容修订、版本与修订、配方摘要、RAW 引擎和解码器、渲染管线版本、目标像素尺寸、方向/几何状态、输出色彩配置和预览质量等级。

不能只用文件路径和宽度作为缓存键。换解码器、修改裁剪或源文件被替换后必须得到新键；旧文件由正常淘汰机制移除。

16.3 淘汰规则

优先淘汰最久未用的可重建大预览，保留当前视图和即将使用的少量邻图；图片数量大时不要反复删除又重建同一个工作集。渲染到临时名称，完成后原子发布缓存，避免读取半个预览。

低磁盘余量时停止预生成；用户仍可看已有内容。固定预览只有明确取消固定或用户选择删除时移除。缓存目录被手工清空后可重建，不应导致目录损坏。

16.4 统一任务中心

导入、索引、渲染、导出、外部回收、文件操作和备份使用统一任务模型。每类任务说明单位：文件数、照片数或字节，不混用统计。

状态包括排队、运行、暂停、取消请求、已取消、成功、部分成功、失败和需要用户处理。任务失败有可以定位的文件项，重试只处理必要项，不能重复覆盖已成功输出。

优先级建议：活动图片显示 > 明确用户操作 > 用户导出 > 当前选择的预览 > 后台索引和预生成。文件事务和数据库提交进入关键步骤后，取消只阻止下一步，不把不完整状态当作已回滚。

16.5 应用退出与恢复

退出前提交已完成编辑动作并持久化任务状态。遇到尚未安全结束的文件步骤时，给出真实状态而不是直接终止。意外退出后先恢复操作日志，再调度正常扫描，避免恢复逻辑和增量监听同时修改相同文件。

恢复后的导出任务只在冻结输入仍可确认时继续；原片已改变或引擎不可用时暂停并说明。不能在重启后用新配方替换之前排队的配方。

17. 输出、命名与隐私

17.1 输出请求必须不可变

用户点击导出时冻结资产/版本/修订、源修订、目标格式、尺寸、质量、色彩配置、元数据策略和命名规则。排队中修改编辑参数，不改变现有请求；用户可以取消后重新导出。

输出结果报告区分已生成、因相同任务跳过、冲突、源离线、显影失败、写入失败。每个成功结果记录文件路径、实际尺寸、格式与来源版本。

17.2 命名和冲突

提供有限的文件名模板：原文件名、拍摄日期、序号、版本名。对路径分隔符、非法字符、大小写冲突和 Unicode 规范化进行平台测试，不通过字符串拼接构造未经检查的路径。

默认策略为生成新名称或要求确认；不覆盖原片，也不把输出目录设成与原片同路径的默认值。覆盖用户已有成片属于高风险操作，V1 可先不提供自动覆盖。

17.3 元数据预设

“分享”预设默认移除 GPS 和设备序列号等敏感信息，保留必要的方向、正确色彩配置及用户选择的作者/版权；“保留拍摄资料”明确显示将保留哪些字段。用户选择原片副本导出时，必须说明它会保留原文件中的全部元数据。

输出图像经过几何变换后更新尺寸、方向和相关标记，不能保留导致二次旋转的旧 EXIF Orientation。已有真实性签名或来源凭证不能随意复制后声称仍有效；V1 不宣称创建或维持内容凭证认证。

17.4 数据迁出包

V1 提供目录清单和可选的资产资料包。清单包含稳定资产 ID、文件相对路径、可用性、评级/标记、关键词、集合关系、采用版本、编辑配方和外部成片关系。默认不输出设备授权书签、访问令牌或用户完整本地路径到对外分享包。

包可以只含管理数据，也可以显式包含原片副本和成片；界面区分清楚，执行前估算容量。自有配方可读并不意味着其他编辑器能执行，文档必须说明这一限制。

18. 备份、目录修复与数据可持续性

18.1 备份范围

目录备份保护管理记录、集合、版本、配方、迁移和任务关系；原片备份保护磁盘文件；成片备份保护已输出成果。这三件事分开解释和展示，不能把目录备份命名成“照片已安全备份”。

默认在目录 schema 升级前备份，另外提供手动备份和可配置的周期提醒/在 App 运行时触发的备份策略。用户需选择备份位置；同一块磁盘中的第二份目录只提供有限恢复能力，不能抵御整块盘损坏。

18.2 一致快照

使用 SQLite Backup API 等有一致性保证的方式取得数据库快照，并配套保存必要清单；不能趁数据库运行时仅复制 .sqlite 主文件。SQLite 官方提供在线备份接口，但仍需处理目标写入失败和备份中断。S22

备份先写入临时包，验证目录完整性、引用关系及版本信息后发布。失败包不能混进“可恢复备份”列表。轮转删除旧备份之前先确认新备份成功，不能先删旧的再尝试写新的。

18.3 恢复流程

用户选择备份 → 检查兼容性 → 在新目录恢复 → 做完整性检查 → 重新授权照片根目录 → 重新定位缺失内容 → 展示恢复报告。

恢复默认不覆盖当前唯一目录。目录可能恢复到旧时间点，外部文件已经改变时要标记不一致，而不是把现实文件当作错误直接覆盖。

18.4 目录检查器

提供检查：数据库完整性、孤立关系、无效采用版本、失联根目录、缺失文件、悬空任务、不可解码缓存、长期未完成外部工程。修复先生成计划；可重建预览可以重建，用户数据不能被“自动修复”静默丢弃。

任何自动修复都要留下报告。无法确定的对象保留并标记，不以删除记录作为通用修复方式。

19. 分发、许可证、安全与维护

19.1 分发路线

Apple Developer 支持通过 Developer ID 签名并公证在商店外分发 Mac 软件；这可作为首轮完整流程验证和首发候选。S23

默认先维护一条功能代码主线。工程初期另建最小沙盒验证目标，验证目录授权持久化、外置盘重连、打开外部编辑器、结果回收和目标路径写入。是否同时上架 Mac App Store，依据测试和当时审核规则决定，不假定外部工具行为可原样搬入沙盒。S07

独立分发不等于无限权限。仍以用户显式选择的目录为访问范围，不默认扫描全盘，不把全面磁盘访问作为首次启动前置条件，不关闭系统安全机制。

19.2 最少权限

文件读取、目标写入和外部工具选择分别授权。安全作用域书签需要处理过期、重新授权和访问结束；保存路径字符串不能代替有效授权。S07

Apple Events、辅助功能、全盘访问等不属于本产品默认必需权限。某个外部适配器确有需要时单独说明用途，不能给全部用户申请。

诊断默认只记录错误类别、任务阶段、耗时、格式和匿名化标识，不记录照片内容、GPS、完整文件路径和私人关键词。发送诊断包需用户确认并可预览内容。

核心功能无云端原片依赖。崩溃报告、许可证验证和更新检查分别说明，不在用户不知情时上传原图或用于训练。

19.5 付费与维护边界

先验证用户是否愿意用它替代日常管理流程，再确定价格。推荐评估一次性购买当前大版本或可选付费大版本更新；不在无成本估算时承诺终身适配全部相机、系统和外部编辑器。

试用或授权失效不应锁死用户数据：至少保留已有目录的阅读与管理信息迁出。付费策略不能迫使用户付钱才能取回评级、集合和原片路径清单。

20. 质量目标与性能预算

本节数值是首轮目标值。G1/G2 应在真实硬件和数据上记录测量，再形成最终发布阈值。不得拿这些数字写宣传材料。

低配测试可先以 8GB 统一内存作为候选，不代表用户的 Mac 已确认是此配置。对外支持声明以实际测试为准；Intel 是否支持属于单独决策，不凭模拟运行确认。

采用固定的肤色、白色/灰阶、强饱和颜色、高光、阴影、高感、细纹理和横竖方向样本，检查明显色偏、色阶断裂、裁切、方向和细节。与 LRC 比较的目的在于判断是否满足需求，而不是把 Adobe 的默认输出设为唯一真值。

记录系统显示相关设置；不同设备视觉比较不能在不控制条件的情况下直接下结论。未建立样张和测量规则之前，不宣称“专业级色彩准确”。

21.4 立即阻断发布的情况

任何未经授权的原片改写、误删、错误照片关联、元数据静默丢失、目录不可恢复损坏、预览与输出显著且未说明的不一致、不能保住唯一外部成片，以及通过伪成功掩盖文件操作失败，均为发布阻断项。

界面缺少次要动画可以延期；上述问题不能用“已知问题”绕过。纯 UI 演示、只有编译通过、或只测一张 RAW，不构成任何完整关卡通过证据。

22. 实施阶段与通过关卡

阶段按依赖和证据推进，不以“写了多少页面”或日历时间判断完成。下面没有开发工期承诺；真实投入应在关键验证后再估算。

G0：项目与样本基线

完成仓库结构、本文入库、实际硬件记录、样本清单、危险操作测试副本和初始依赖/分发决策。核对已有图片 App 可复用模块，不先搬进整个工程。

**产物：**环境清单、样本 manifest、范围确认、初始 ADR、可运行的最小 Mac 应用与测试入口。

**通过条件：**已知真实相机/文件模式；没有把示例相机当用户设备；可以重复运行同一组测试。样本尚缺时可以实现无关模块，但兼容结论保持未验证。

G1：显影与颜色可行性

做最小技术验证：读取 RAW、探测能力、调整曝光/白平衡、裁剪、预览、输出 JPEG/TIFF，并记录画质、耗时、资源和引擎版本。无需先开发完整图库。

**产物：**真实文件兼容矩阵、统一渲染契约、前后与输出回读样本、性能记录、G1 决策报告。

**通过条件：**目标主力文件模式满足个人基础处理要求；无明显无法解释的显示/输出差异；不存在资源不可控问题。失败时分清 API 缺口、实现问题和画质不满意，不默认改成自研 RAW。

G2：可信图库与文件操作

实现目录、引用/复制导入、基础元数据、图库分页、评级/集合、预览预算、离线与重新定位、文件操作日志和备份框架。先在副本上测试危险路径，再接入真实日常图库。

**产物：**可每天使用的管理内测版、文件安全回归报告、目录 schema 与恢复报告。

**通过条件：**重扫不重复；拔盘不误删；管理变更可保存；复制/移动中断可恢复；数据库与文件关系始终可解释。

G3：完整拍摄流程

接入正式基础编辑、版本、批量调整、输出队列和外部精修往返，补齐单图/比较/键盘工作流及未完成任务恢复。

**产物：**一整组真实拍摄从进入硬盘到归档的演示和测试记录，不是分别录几个孤立功能。

**通过条件：**至少一种外部编辑器完整验证；原片、配方、成片和任务关系正确；输出来自冻结版本；主要交互能连续完成。

G4：迁移、性能与破坏性测试

验证 LRC 标准元数据/成片迁移、真实与规模数据性能、错误文件、空间不足、授权失效、任务中断、升级与恢复。

**产物：**完整兼容说明、基准报告、迁移报告模板、全部阻断用例结果和已知限制清单。

**通过条件：**第 21 节阻断项为零；性能达到经评审冻结的预算；不支持的场景有安全行为；数据可迁出。

G5：正式发布准备

确定发行与付费方案、签名/公证/安装更新、隐私说明、依赖许可、用户帮助、试用与退出行为。涉及商店版本时单独验证沙盒、购买恢复和审核需要的说明。

**产物：**发布候选包、校验信息、最终支持矩阵、恢复指南、许可清单、发布检查表。

**通过条件：**干净环境可安装运行；无开发目录依赖；断网核心可用；升级能保住已有目录；真实测试者可完成关键任务。

  • □ 文件移动/复制/重命名/废纸篓在中断、冲突和磁盘满时行为安全。
  • □ RAW/JPEG/ACR/XMP 与外部成片关联不丢失、不误配。
  • □ 拔盘与授权失败不导致批量删除管理记录。
  • □ 缓存清理不会删除用户作品、配方、固定预览或未完成工程。
  • □ 备份、恢复与目录 schema 升级实际执行通过，不只是存在菜单。
  • □ 活动数据库不放网络/同步目录；SQLite 构建和补丁来源有记录。
  • □ 已通过相关低配与规模测试，数值来自真实日志而不是方案目标。
  • □ 外部编辑至少一个工具完整验证，通用手动回收路径始终可用。
  • □ 标准元数据和全部管理信息可迁出，不宣称 LRC 效果一比一兼容。
  • □ 核心离线使用、试用结束后的资料读取/迁出按产品政策工作。
  • □ 干净 Mac 环境可安装，签名、公证/审核与更新路径验证通过。
  • □ 隐私、依赖许可证、支持矩阵、恢复指南和已知限制随版本发布。
  • □ 第 21.4 节所有发布阻断项均已关闭并有验证证据。

27. 后续扩展池：不进入 V1 的并行开发

第一版稳定且确有使用证据后，再依次评估：原位 XMP 双向同步、LRC 官方插件迁移集合/虚拟副本、更多外部工具适配、Apple Photos 库、智能选片辅助、受控曲线/HSL、HDR 显示与输出、iPad 只读/选片配套等。

每个扩展都需要说明它补足了哪条真实工作流、会影响哪些数据和兼容承诺。AI 搜索、自动修图、云同步、视频和模板商城不因“可以接一个模型或 SDK”就自动进入路线图。

现有装饰图片 App 可以未来作为一个外部输出目标：从本 App 送出已确认成片，进行边框水印或拼图。两个产品可以连接，但不要把本 App 重新做成装饰功能的大集合。

28. 方案结论

本项目值得验证的不是“能不能再写一个修图软件”，而是能否做出一个愿意长期把照片放进去管理的工具。

最优先掌握的能力是目录与资产关系、选片、文件操作安全、版本与成片追溯、离线与恢复。RAW 采用系统主路线，专业处理通过可追踪的外部交接，既保留实用性，也避免被专业成像底层拖离产品目标。

实施顺序：先确认真实 RAW 的显示与输出质量，再建立可信目录，然后完成拍摄全流程，最后依据故障、迁移和性能测试决定发布。

如果最终只剩更便宜的看图器，方案没有成功；如果为追平 LRC 而陷入自研全部成像技术，同样偏离初衷。成功标准是：管理足够完整、日常处理足够好、资料可控且不被锁住。

附录 A. 关键状态与错误契约

状态不能全部塞进单一 isAvailable。至少拆为以下几组，以便界面和恢复逻辑作出正确判断。
